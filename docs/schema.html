EverChat schema draft

The tables of EverChat's database, for many chats: one schema for every build, in a local SQLite file and on MariaDB. Draft 3, for review, before the code.

This page follows docs/design.md ("Tenants and isolation", "The database", "Messages in, events out"), which wins where the two differ, and docs/state.md, which lists the 63 pieces of state that the old code keeps. Draft 2 checked the schema against the factory's seat runtime interface (everturn ADR 0186 and packages/bridge/src/runtime/types.ts); section 13 keeps that check. Section 2 says what the code has today. The question numbers in brackets ([Q9]) are those of the design.

The words on this page are those of GLOSSARY.md.

Decided already:

  • The local driver is @effect/sql-sqlite-bun (Effect's SQL client over bun:sqlite). Bun bundles SQLite 3.53.4. The server database is MariaDB 10.11 [Q7].
  • synchronous = full: each commit is on the disk before the call returns. We will revisit this if it feels too slow.
  • Greenfield: no old chats, and no migration from the old files.
  • Model calls go through the author's inference gateway, with an API key, for both OpenAI and Anthropic. The sign-in with a ChatGPT plan is for later. Its tokens will then go in the database.
  • Imports of old Claude Code and Codex sessions are out of scope. Their tables and the imported flag are gone.
  • The kind of EverChat's own messages is asst (section 14).
  • Version 1 deletes nothing: every turn's items and every call's whole output stay in the database, so that they can be measured. Deleting is a question for version 2. No erasure of a tenant in the first version [Q9].
  • Background shells are for version 2. Version 1's background work is a subagent. EverChat has two uses. In the factory, it is a chief of staff that hands coding work to mature harnesses (Claude Code, Codex). Alone, for example as a person's main assistant, it has no other harness, and it uses its own subagents a lot. So subagents must be cheap and solid.
  • OpenAI goes first, then Anthropic.

What changed from draft 2

  • New: every name has the prefix everchat_ (section 1).
  • New: everchat_tenant. everchat_chat has a row for each chat, with its tenant, its UUID as 16 bytes, and the counter of its events (seq).
  • New: keys (chat, n). Each reference carries the chat, and deletes cascade from tenant to chat to rows.
  • New: everchat_event, a row for each event but a piece.
  • New: more that the database refuses: a chat keeps its id, its tenant and its UUID, also through its rowid; a row of a launch, a turn, a call or a view keeps its chat and its key against an update (a REPLACE is a delete and an insert, and through the rowid it can move a row: section 1); every table whose rows have neither updated nor ended refuses an update; a message's images go only with the chat (section 1).
  • New: each column has its SQLite type and its MariaDB type. The SQLite DDL is one block (section 8).
  • Changed: the partial indexes became forms that run on both: a generated column live for the live launch, and plain indexes with chat in front.
  • Changed: no migrator. The local file gets its schema made whole, with a mark, and a file of another schema is refused (section 1).
  • Went: the rule "One home, one database, one chat" (the design puts many chats in one database); the migrator and its table effect_sql_migrations; the tables agent and agent_msg, which no code uses, and whose cycle of references with turn has no proved form on MariaDB (everchat_turn.agent stays a plain column until agents come); the table credential, which is later work (below); and the table of the originals of images, which belong to the client [Q35, Q44].
  • Later work, not in this schema: the lease and the epoch of a deployment (they come with the server package), a row for the deployment, wake-ups, grants, and credentials (the sign-in tokens of a ChatGPT plan).

1. Rules for every table

  • One schema for all builds. The local SQLite file and a MariaDB schema have the same tables, columns, keys and names [Q15, Q24, Q46]. On a server, one MariaDB schema holds one deployment: all its tenants and their chats. The local file holds one row of everchat_tenant, made with the file, and the chat of its home: the variable EVERCHAT_HOME names a directory (the home), and the database is one file in it. So a test of two tenants runs on SQLite.
  • The prefix. Every name that is unique in a schema has the fixed prefix everchat_, written out in each statement: each table, the view, each index and each trigger. No statement builds a name. In SQLite an index's name and a trigger's name are unique in the whole file, so they take the prefix too. Foreign keys and checks have no names. The indexes that SQLite makes by itself for a unique or a key are named sqlite_autoindex_…: they are SQLite's, not ours.
  • Tenants and chats. A tenant is a separate company, possibly a competitor, and has many chats. everchat_tenant.id is the tenant's UUIDv4 as 16 bytes; it comes from outside [Q9, Q16]. A chat has an integer id inside, made by the database, and a UUID outside: 16 bytes, made when the chat is made, and text only at the store's edge. Two tables are shared lists, with no text of a tenant: everchat_kind and everchat_pick. Every other table but everchat_tenant is a table of a chat.
  • Keys (chat, n). Each table of a chat has the column chat, and its primary key starts with it: (chat, n), or chat and the table's own coordinates ((chat, i) for a message, (chat, l, i) for a node, (chat, name) for a view, (chat, turn, n) for a turn's item). The program makes each n in the transaction of its write: one more than the chat's highest n in that table, from 1. An event's n is the chat's counter plus 1 (everchat_chat.seq, section 4). A table's own coordinates start at 0: a message's i, as the tree needs, a turn's item in its turn, and a message's image in its message. One writer for each chat (below) makes this safe.
  • The tenant boundary. Every statement on a table of a chat has the chat in its where or in its key. A reference to a row of a chat carries the chat: it is a foreign key (chat, x) to the parent's key (chat, n). So a row of one chat cannot point to another chat's row: the database refuses it. Each statement on everchat_chat names the tenant: where tenant = ? and uuid = ?. A chat's id, its tenant and its UUID never change: the database refuses an update that names one of them (in SQLite the trigger everchat_chat_no_move, on MariaDB the user's rights, below), so no update moves a chat, with its history, to another tenant. SQLite fires no trigger of update of id for an update of the id's other names, rowid, oid and _rowid_, so the trigger everchat_chat_no_rowid refuses an update that changes the id under any name. A row of a chat keeps its chat and its key too: the database refuses an update that names the row's chat or a column of its key, in every table with a column chat, also when it sets the value that the row has. The four tables whose rows may change (everchat_launch, everchat_turn, everchat_call, everchat_view) do it in SQLite with the trigger everchat_<table>_no_move, on chat and n (a view's chat and name); the others refuse every update (below). So no update moves a row to another chat, plain or with or replace over that chat's own row; nor does the do update of an upsert (insert … on conflict … do update set chat = …), which these triggers refuse as well. A REPLACE (replace into, insert or replace) is no update, and no guard of a row's chat or key runs for it: it deletes each row that it meets, on the table's rowid, its key or a unique index, and then inserts its row, so it passes where those deletes and that insert pass (the rule of a REPLACE, below). So in SQLite a REPLACE that gives a row's hidden rowid with another chat takes the row out of its chat and puts a row with the same rowid and values into the other chat, of another tenant too. That holds in each table of a chat with a rowid where a delete passes: everchat_launch, everchat_turn and everchat_call, and everchat_head, everchat_turn_item, everchat_image, everchat_usage and everchat_log. It passes for a row with no child, and for a row whose children may all be deleted: the cascade of the references inside the chat deletes them, as for a delete (a launch's turns and log rows, a turn's items, calls and usage, a program's functions, the turns of a head). It is refused when that cascade reaches a message, an event or a message's image: everchat_msg_no_delete, everchat_event_no_delete and everchat_msg_image_no_delete refuse it, as they refuse the delete. A row of the other chat that it meets on its key or on a unique index goes too, with its cascade, as far as that delete passes (a call meets the other chat's program with the same turn and vendor id). everchat_view has no rowid (its key is (chat, name)): a REPLACE there writes only the view of the chat that it names, a new one or over that chat's own view, and the view that it copies stays. The store has no REPLACE. On MariaDB a REPLACE needs the right DELETE (a trial on 11.4.13 refused one to a user with INSERT and no DELETE, for a key that is there and for a new one), and the user has DELETE on everchat_log only (below). A test reads the rule from the file: in each table with a column chat, an update that names chat or a column of the key is refused, and so is a change of the chat's rowid. A tag of the deployment makes and finds chats, only by their tenant and their UUID, and gives a Store for one chat; a chat of another tenant is not found, with the same answer as a UUID that does not exist. No member of Store takes a chat's id. A test with two tenants checks it [Q5, Q8, Q13].
  • Deletes cascade from tenant to chat to rows [Q9]. everchat_chat.tenant refers to the tenant on delete cascade; each table's chat refers to the chat on delete cascade; and each reference inside a chat cascades too, so that the rows of a chat can go in any order (MariaDB checks a reference at once, and has no check deferred to the end). A reference to a shared list does not cascade, and no row of a shared list (everchat_kind, everchat_pick) is deleted, in use or not: in SQLite the triggers everchat_kind_no_delete and everchat_pick_no_delete refuse every delete, and so every REPLACE, of a row. No reference cascades into them, so the erase of a tenant does not reach them. In SQLite the trigger everchat_chat_no_delete lets a delete of a chat's row pass only when its tenant is gone, so the one way to erase a chat is the delete of its tenant. The delete of a tenant's row is that erase, so a REPLACE of a tenant's row would be one too: the program makes a tenant's row once, and no statement of it is a REPLACE; whether the erase of a tenant goes through a state of its own is the plan of the server package. No code deletes a tenant or a chat in the first version. On MariaDB, the composite references (chat, x) … on delete cascade, with the reference of everchat_call to itself, are not proved here: the checks of the mariadb package prove them.
  • One writer for each chat. In the local file, one process owns it: everchat_launch shows which, and a chat has at most one live launch. On a server, one active process for each deployment, with a lease row and an epoch that each write checks [Q22]; they come with the server package. Other programs may read the local file (WAL mode allows that), for example a backup.
  • One event, one transaction. Each event (a message sent, a step done, a function started) writes all its rows in one transaction. After a crash, an event is there whole or not at all. Each event but a piece (text, thought, program) also writes a row of everchat_event, in the same transaction, with n from the chat's counter [Q10, Q17]. Section 9 lists the events.
  • Append only where the memory needs it. A message's id never changes and is never reused. The tree math depends on it (node (l, i) covers messages i·2^l on). everchat_msg, everchat_msg_image, everchat_node and everchat_event refuse an update and a delete: a message's images are part of it, and go only with the chat. The shared lists everchat_kind and everchat_pick refuse both too, in use or not: a message's kind and a turn's model are read through them. Every other table whose rows have neither updated nor ended refuses an update (the rule of created and updated, below). A bug in the program then cannot rewrite the chat's history.
    • In SQLite, triggers do it. A trigger that refuses a delete lets it pass only when the row's chat is gone. SQLite deletes the chat's row first, then runs the cascade, so the cascade of a deleted chat passes and every other delete is refused. A REPLACE (replace into, insert or replace) deletes the row that it meets, and with recursive_triggers = on (below) that delete runs the delete trigger, so a REPLACE of a message, a message's image (its row of everchat_msg_image), a node or an event is refused too: each of these needs the pragma. A delete or a REPLACE of an image that a message names is refused as well, through the cascade: it would delete the message's row of everchat_msg_image, whose trigger refuses; a cascade's delete runs the trigger, so this one does not need the pragma. The shared lists everchat_kind and everchat_pick have a delete trigger with no condition (everchat_<table>_no_delete): it refuses every delete and, with the pragma, every REPLACE. Without it, a REPLACE of a kind or a pick in use would pass, and give every message or turn that names it another kind or model: SQLite checks a reference that does not cascade only at the end of the statement, and by then a row with the same id is back. A table that refuses an update has the trigger everchat_<table>_no_update. The tables where a delete passes allow a REPLACE as a delete and an insert: it passes as those two statements would. They are those of them that refuse an update (everchat_tenant, everchat_head, everchat_turn_item, everchat_image, everchat_usage and everchat_log) and the four whose rows may change (everchat_launch, everchat_turn, everchat_call and everchat_view), each as far as its cascade allows; in each of them but the tenant and the view, a REPLACE through the rowid can move a row to another chat (the tenant boundary, above).
    • On MariaDB, the rights of the user do it, with no trigger [Q55]. In the first version the user has DELETE on everchat_log only (the delete of a chat's old lines at its launch). It has no DELETE on the six tables that refuse one (the four of a chat and the two shared lists), and none on a table from which a cascade reaches them; by the references of section 8 those are everchat_tenant, everchat_chat, everchat_launch, everchat_head (through the turn), everchat_turn, everchat_call and everchat_image (through everchat_msg_image). It has no UPDATE on the twelve tables that refuse one. On the five that may change, its UPDATE is a right on the columns that change only: on everchat_chat pick, goal, draft, taken, seq and updated; UPDATE (ended, why) on everchat_launch; UPDATE (status, ended, why) on everchat_turn; UPDATE (status, output, size, shown, pgid, ended) on everchat_call; UPDATE (parts, batch, updated) on everchat_view. So no row's chat or key changes there either (not proved here: the checks of the mariadb package prove these rights). MariaDB has another name for a chat's id: _rowid names a primary key that is one integer column, as id is (a bigint auto_increment). It needs no rule of rowid all the same: the wall is the user's UPDATE right on the named columns above, which do not include id, so a statement that names the key another way, as _rowid, is refused too (not proved here: the checks of the mariadb package prove it). A later version that deletes from another table adds that right then. The erase of a tenant needs a right that this user does not have: who does it, and with which rights, is the plan of the server package. That a cascade passes there is not proved here: the checks of the mariadb package prove it.
  • Times are integers: milliseconds since 1970-01-01 UTC. An integer takes 6 bytes, and the ISO 8601 text of draft 1 took 24. The program formats a time when it shows it to the model or to a person.
  • Order comes from ids, never from times. A clock can jump back, and a chat can move to another host. Times are for people.
  • created and updated. Every row of data has created. A row that can change also has the time of its last change: updated, or ended for a row that changes only once, when it closes (a turn, a call, a launch). A row that can never change has no updated. That absence is a statement, and one rule enforces it: a table whose rows have neither updated nor ended refuses every update (in SQLite its trigger everchat_<table>_no_update, on MariaDB no UPDATE right). A test reads the rule from the file: each table has updated or ended, or that trigger, never both and never neither.
  • Who, what, when, where, why come from the structure, not from five more columns on each row. Section 14 has the table.
  • Small numbers for repeated values. A value that repeats on many rows of a large table, and whose list can grow, is a small integer that points to a small table (everchat_kind, everchat_pick). SQLite cannot change a check list without a copy of the whole table, so a list in a small table is the only cheap way to add a value later. A status on a small table stays a word with a check, because it is easy to read.
  • STRICT tables in SQLite: SQLite then checks each column's type.
  • Well-formed text. SQLite writes a lone surrogate as U+FFFD. So the program makes every string well formed (toWellFormed()) before it uses it, and the text in memory always equals the text on disk. size is the length of that text in UTF-8 bytes.
  • Flags are integer not null default 0, checked to be 0 or 1.
  • JSON goes in text columns, and only for values that the program always reads and writes whole (a view's parts, a vendor item). Anything the program searches or joins on gets its own column.
  • Two DDL texts. SQLite and MariaDB cannot run one DDL text: strict, the types, without rowid, the triggers, the table options and the time function of the view differ. Section 8 holds the SQLite text, whole and in order. The tables of sections 4 to 7 give each column's SQLite type and its MariaDB type; not null, the defaults, the checks and the keys are the same in both. The MariaDB text is .sql files in the form of skeema, one for each table, and they come with the mariadb package. Each MariaDB table states its own character set [Q46]; the research gives the options engine = InnoDB default charset = utf8mb4 collate = <one collation> row_format = dynamic (docs/research/mariadb.md, "What fits"), and the collation is not settled here.
  • The schema is made whole, never migrated [Q55].
    • The local file: on an empty file (no table of ours), EverChat runs the whole DDL of section 8 and sets the mark pragma user_version to the schema's number, in one transaction. A file with this schema's mark opens as it is. Any other file (another mark, or tables with no mark) is refused, with a message that tells the person to move the file aside; nothing deletes a person's file. A change of the schema means a new file and a new mark. This schema's mark is 6.
    • MariaDB: an administrator applies the .sql files with skeema. The server build has no migrator and never changes the schema. At each start it compares each table's definition with its files, and stops with an error that names a difference.
  • Pragmas at open: journal_mode = wal (the driver sets it), synchronous = full, foreign_keys = on (SQLite checks no reference without it, and it is set on each connection), and on each connection that writes recursive_triggers = on (a REPLACE deletes a row, and without this pragma SQLite runs no delete trigger for it). The driver waits up to 5 s on a locked file and starts each write with BEGIN IMMEDIATE.
  • The inspector's version stays pragma data_version in the local file: it is no column of the schema, and everchat_chat.seq does not replace it (a compaction writes no event).
  • The word call is reserved on MariaDB, so a statement there writes the column call as `call` (docs/research/mariadb.md, "Does mysql.md hold on 10.11?"). The tables need no quotes: the prefix makes everchat_call and everchat_usage plain names.

2. What the code has

True at this commit. The code (packages/sqlite/src/schema.ts) has this page's schema, the statements of section 8 in their order, and its mark 6; packages/sqlite/src/database.ts sets the block's two pragmas, foreign_keys and recursive_triggers, on the connection that writes. A file can hold the chats of many tenants. The tag of the deployment, Chats (packages/core/src/store.ts, built in packages/sqlite/src/sqlite.ts), makes a chat of a tenant (and the tenant's row when it is not there, with a select and an insert, never a REPLACE), and finds a chat only by its tenant and its UUID: the one statement that finds a chat is where tenant = ? and uuid = ?. It gives the Store of one chat, which takes the chat with a launch row and ends that launch when its scope closes, and the chat's reads. A UUID that no chat has, a chat of another tenant and a text that is no UUID get one answer, the error NoChat, with no field. The local layers have one tenant and one chat in the file: the first launch makes, in its transaction, the row of everchat_tenant (the 16 bytes of a new UUIDv4) and the chat's row, and a later launch makes none; then they find the chat and take it on the same path as the tag. Each store is bound to its one chat: each of its statements on a table of a chat names that chat, and each statement on everchat_chat names the tenant. The program makes each n, from 1 in each chat, and a table's own coordinates from 0 (a message's i, a turn's item, a message's image); the store gives a row's n as its id, and the chat's UUID as text. The store's member addEvent writes an event's row of everchat_event with the chat's seq plus 1, and sets seq to it. The turn loop (packages/core/src/turn.ts) calls it in the transaction of each event of section 9, one transaction for each event, and a listener gets a chat's events in the order of their numbers. A message of a person can carry the key of its sender: the store's member append takes it for the first page of what it writes, checks its form, and writes it in the message's insert; the index everchat_msg_sender_key refuses a key that the chat has; and the read keyed gives the message of a key in the chat, its pages and the number of its accepted event, or none (each of its statements names the chat). The turn loop does not give a key yet. The test of every member with two tenants is packages/sqlite/src/tenant.test.ts. Still to come: a read of the events, with the local host, and the lease and the epoch of a deployment. Each later bead keeps this section true.

4. Tenants, chats and launches

everchat_tenant

Each tenant of the deployment. EverChat keeps no accounts and knows no persons [Q19, Q33, Q39]: a tenant is its UUID, which the backend gives. The local file has one row, made with the file, with a new UUID.

  • A delete of a chat cascades to every row of the chat, in every table of a chat. SQLite triggers: everchat_chat_no_delete, which lets the delete pass only when the chat's tenant is gone (section 1), everchat_chat_no_move: a chat's id, its tenant and its UUID never change, and an update that names one of them is refused, also when it sets the value that the row has; and everchat_chat_no_rowid: an update that changes the id through rowid, oid or _rowid_, for which SQLite fires no trigger of update of id, is refused too. A statement on this table names the tenant (section 1).
  • On MariaDB the user's UPDATE on this table is a right on the columns pick, goal, draft, taken, seq and updated only, with no trigger (not proved here: the checks of the mariadb package prove it). MariaDB has another name for id, _rowid, as for any primary key that is one integer column; the wall is this right on named columns, which do not include id, so a statement that names the key another way, as _rowid, is refused too (not proved here: the checks of the mariadb package prove it).

taken answers "which messages wait for a turn?" after a restart: the user and work messages with a higher id. A message that comes while a turn runs is logged at once, but the turn takes it in only after its step's results. The old code kept this in memory only.

uuid is the chat's id for the world outside. The factory calls it the session id, and it must be the same at every launch (ADR 0186, rule 3). The store turns it into text (8-4-4-4-12 hex) at its edge, and back.

seq is the chat's counter of events: an event's n is seq + 1, and the same transaction sets seq to it (section 7). One writer for each chat keeps the numbers in the order of the commits [Q10, Q17].

everchat_launch

One row for each load of a chat: in the local use, each start of the program (items 31, 60). It does four jobs:

  • Owner. A launch with no ended is live, or it crashed. The index everchat_launch_live lets at most one such row exist for each chat. A new start checks whether that process still runs. If it does, the new start stops. If not, it closes the old row with why = 'crash' and adds its own, in one transaction. A launch that ends in order writes its own why: exit, signal (it was interrupted), or error (it failed, and still closed the file).
  • Leftover shells. Each shell gets the launch's run_tag in its environment. The next start stops each process that still carries an old tag.
  • Where. Other rows point to the launch that wrote them. That gives the host, the directory and the program's version for every message, without three columns on each row.
  • The factory's session record. ADR 0186 keeps one record per launch of a continuous chat. This table is that record.

The output limit

Decided: the database keeps a result whole, and the model is shown a limited form. Three things happen when a program's result is over the limit:

  1. The model gets the head and the tail, with a line between them that says how much was left out and where the whole text is. The echo message in the log is this limited text, so the memory holds what the model saw.
  2. The amount is recorded: size is what was produced, and shown is what the model got.
  3. The whole text is written to a file in a private directory under the system's temporary directory (/tmp), named after the call's id: everchat-<user id>/<chat's uuid>/<call id>.txt. The model can read or search it with its normal functions. The file is a copy, not state. If it is gone (after a reboot, for example), the function result(id) writes it again from everchat_call.output, and gives the whole text to the program that called it. The directory is used only if EverChat owns it and no other user can enter it. If not, the line names only result(id). result(id, from, to) gives a part of the whole text to a program: its characters from from (0 when not given) to before to (the end when not given), so that a chat with no file reads the rest in parts.

The default limit is 30,000 characters. The config file (config.json in the home) sets another with its limit, a whole number of characters from 2,000 to 1,000,000. Three sources agree on about that size:

Two points come from code mode:

  • The limit is on what the model reads, not on what a program gets. A function gives its whole result to the program that called it, so the program can search or parse it. The limit applies to the program's own result, which is what goes to the model.
  • A second, hard limit is still needed. A command that never stops printing must not fill the memory or the database, and SQLite cannot store a text over 1 GB. Decided: 64 MiB, the size at which Claude Code cuts its saved file. Past it, the output ends there and the command is stopped. size is the size of what was kept.

Two more limits keep a program from holding its turn for ever. They are not in the schema, and they are here because they end a call:

  • The time limit of a command: 600 seconds, or the seconds that the program gives to shell. The command is then stopped, and its result says so.
  • The compute limit of a program: 60 seconds with no function at work. A program has no timers, so one that computes for that long is in a loop. A program may wait for a function as long as that function takes.

One system prompt for the chat and its subagents (decided)

In the old code a subagent has its own system prompt, so it cannot read the chat's cache and pays for the whole view again. Decided: a subagent gets the chat's system prompt, and a message after the view tells it that it is a subagent.

The old code already does this for compactions. Its one system prompt says: "Each call to you is a turn or a compaction: the view below is followed by the user's new message, or by a task starting Compaction:." The rules for a compaction are a section of that prompt, and the text after the view chooses the role. A cheap compactor model follows it.

The design:

  1. One head. The chat and its subagents send the same system prompt and the same tool list. Code mode makes the tool list equal for free: there is one tool.
  2. The system prompt names three kinds of call: a turn, a compaction, and a subagent task. The rules for a subagent (today's SUB text) become a section of it, next to the compaction section.
  3. The request is: the head, the chat's view, the open devices, then a block that starts Subagent task: with the agent's name and its log. The first two parts are bytes that the chat already sent, so the agent reads them from the cache.
  4. Code enforces what a subagent may do, not the prompt. A subagent's program that calls a function only the chat may use (to start an agent, for example) gets an error.
  5. The pick is a choice per agent. On the chat's pick, the agent reads the chat's cache. On a cheaper model or another effort, it has its own cache, as today, but still the same prompt.

Is a message strong enough? Yes, if the system prompt itself defines the mode. Then the message does not argue with the system prompt ("you are EverChat" against "you are a subagent"). It starts a mode that the system prompt describes, and it is the last thing the model reads before it acts. Three sentences of today's subagent prompt must stay in that last block, because they guard against the known mistakes: do the task and not what the user's last message says; the final reply is a report to EverChat and not to the user; the view is context only.

What it saves. A view is 64 to 128 KB. Today each group of agents that start together pays for it once at the full price, and so does each new task for an idle agent. With one head, they read it from the cache. A computer task gains nothing: it has no view, and it has another tool.

For the schema: the tables of agents come with agents. An agent's turn will point to the same everchat_head row as the chat's turns.

10. What a restart does

  1. Take the file. Open it. An empty file gets the whole schema and the mark; a file of another schema is refused (section 1). Find the file's one chat, or make it with its tenant at the first launch. Read the chat's launch row with no ended. If its process still runs on this host, stop. If not, close it with why = 'crash' and add our own row.
  2. Clean up processes. Stop each process that still carries the run_tag of a launch that ended (a shell that a crash left running). The tag is in each process's environment, as EVERCHAT_RUN. A launch that ends cleanly stops its own processes: each shell's process group, then each process that carries its tag.
  3. Load the memory. Read both views from everchat_view, byte for byte. Read the nodes that they and the tree above them need. Find the nodes to build with a query (nodes not built whose two halves are), not with a walk of the tree.
  4. Close the cut calls. Set each call still running to cut, the functions first. For a cut program, log its tool and an echo that lists its functions: which ended, with the start of its result, and which one was cut ("It may or may not have finished."). Each line has the call's id, so that result(id) gives a whole result. Add the same text as its result in the turn's items. The program is not run again. A program that the person stopped gets the same list.
  5. Continue the cut turns. For each turn still running, build the request again from its head and its items, and send the next step. The prefix is the one sent before, on the same pick. So it reads the vendor's cache and keeps the thinking blocks valid. Each such turn gets a start event.
  6. Start the compactions again. Their state is derived, so nothing is stored for them. A compaction that was cut is asked again.

Each step reads and writes the rows of the one chat that loads. A hosted chat loads the same way when a message or a client comes for it, and EverChat unloads it after 6 minutes with no work [Q12, Q20]; the lease of the deployment takes the place of the process check of step 1 (it comes with the server package).

ADR 0186 expects step 5: "a continuous chat resumes with the cut turn at its next launch" (rule 3).

11. Hooks, and why the outbox is gone

Draft 1 had a table hook_event: an outbox that kept each event until a hook had run for it, also after a crash. ADR 0186 shows that this is the wrong shape for the factory, for three reasons:

  • A hook speaks about the live process. The bridge accepts a hook's event only from a direct child of the runtime process that runs now. An event of a process that died, sent late by the next process, would describe a state that is gone. When EverChat dies, the bridge sees the exit itself.
  • A hook can answer. The session-start hook gives text for the model. The hook before a shell command can refuse it. The hook after a program can add text for the model (the factory's "steer mail"). So EverChat must wait for each hook, at the point where it runs.
  • What must last is the answer's effect, not the event. That effect already has a place: text for the model becomes a message and a turn item, and a refusal becomes a call with status denied and the reason as its output.

So there is no hook table now. Hooks come later (hosted chats have none [Q52]), and section 9 marks the points where they will run. The puzzle "how do shell hooks work when the only tool is code mode" has an answer in the ADR (rule 4), which Codex's code mode already follows:

  • The hook before a tool runs for each shell command, not for the program around it. It runs in the shell function on the host side, before the command starts. The hook sees the command text.
  • The hook after a tool runs after each program.
  • The sandbox must have no other way to start a process, and no way to type into a command that already runs. Without both, a command could pass the hook unseen. This is a condition on the code-mode design (how the engine (packages/codemode) runs a program), not on the schema.
  • Each command's shell must be a direct child of the EverChat process, wherever the sandbox runs.

The transcript: a JSONL export (decided)

The interface wants a file of JSON lines that the bridge can follow, and our state is a SQLite file. So EverChat also writes a JSONL file, as an export. The database stays the only state: EverChat never reads the file back, and a deleted file loses nothing.

The file is append only. A line is written once, after its transaction is on disk, and it never changes. The bridge needs this: it remembers a byte position in the file and reads only what comes after. The rule for what gets a line follows from section 3:

  • A row that never changes gets one line (a message, a model request's usage).
  • A row that changes once, when it closes, gets two lines: one at its start and one at its end (a launch, a turn, a call). A reader joins them by id. A call with a start line and no end line is still running, or was cut.
  • A row that changes often, or that is derived, gets no line.

It holds what happened, in full, and not the memory. The tree's nodes and the views are not in it.

One file per launch. Each launch writes its own file, named after its launch row. A file ends with its launch, so the factory's archive can call it done, and a person can delete old files with no loss. One file for the whole chat would never end and would grow as large as the chat. ADR 0186 assumes one file for a continuous chat ("each names the same transcript"), so the adapter's ADR must change that sentence.

After a crash, some rows can be in the database and not yet in the file. Each line carries its row's id, so the next start reads the end of the crashed launch's file, finds the last id of each kind, and adds what is missing there, before it starts its own file. Lines of one kind are always in id order.

Section 14's five questions hold in the file too: each line has its time, its launch, its turn and its call.

What tells the factory that a typed line was accepted (decided)

For EverChat, a turn is one loop: from a first message until a step that calls no tool. For the bridge, a turn start is also the proof that the line it typed was taken: send answers "accepted" at the next turn start, and "refused" after a timeout. The two agree when a message comes to an idle chat. They differ in three cases:

  • A message while a turn runs. It steers the running turn: the model reads it between two programs, as in the old code. No turn starts, so the bridge would answer "refused" for a line that was taken.
  • A message too late for the running turn. It starts the next turn by itself when the running one ends. A turn starts, but later than the bridge's timeout may allow.
  • A turn that continues after a restart. It starts with no message at all, right after the session start.

Decided, with no change to the interface: EverChat has its own event "a message was accepted", sent when the message is in the log (at once, on Enter), and its own turn events. The adapter turns the accepted event and each turn start, also one that continues after a restart, into the bridge's turn start, with the turn's id. One check is left for the adapter's ADR: that the bridge takes a second turn start inside a running turn.

14. Answers to the review questions

The word in place of "unii": asst (decided)

The table stores the number 2, and the word is one row in everchat_kind. But the word matters, because the model reads it before each of its own messages (asst: ...), and the compactor writes it inside summaries. The old code says ever, which is an English word: a summary can read oddly, and a search also finds "every" and "never". asst is the standard short form of "assistant", so a person and a model both read it right with no definition.

It has 4 letters on purpose. The prefix counts toward a node's 512 bytes (Memory.show), so asst: keeps the byte budgets of upstream's unii: : a message is its own leaf, with no request, up to 506 bytes of text. A longer word breaks nothing, but it sends a few more messages to the compactor. The new code uses asst from the start. The old code keeps ever until it moves to ref/, and the ported tests change only that word.

Should kind be a number?

Yes, but not for the space. The word takes about 4 bytes more than the number, on rows of hundreds of bytes: under 1%. The real reason is growth. SQLite cannot change a check (kind in (...)) list without a copy of the whole table. For everchat_msg, the table that grows forever, that copy is the one thing to avoid. With the small table, a new kind is one new row. Statuses on small tables stay words.

All levels of node in one table, or a table per level?

One table. A table per level is a bad idea:

  • The set of tables would grow while the program runs. A schema made whole cannot describe that, and each query needs a table name built at run time, which the prefix rule forbids.
  • It gains nothing. With the key (chat, l, i), the database already keeps each level of a chat together on disk, in order of i.
  • A query across levels becomes impossible. The restart needs one: "the nodes not built whose two halves are".

There are few levels: a million messages make 20. Draft 2 measured three shapes of this one table, with one chat and 800,000 nodes of 200 to 512 bytes:

ShapeFileOne random readOne read in a run at one level

Key (l, i), ordinary table311 MB8.7 µs5.6 µs

All three are fast, and they differ by microseconds, next to requests that take seconds. So the schema keeps the plainest shape, with the chat in front. The reads used a 2 MB page cache and a warm disk cache. All 800,000 rows took 2.5 to 3.3 s to write, in batches, without synchronous = full.

Keep the original image? No (decided)

EverChat keeps only what it sends to the model, and the originals belong to the client, which has them already [Q35, Q44]. So this schema has no table of originals, and an image is one row of everchat_image (section 5). Draft 2 had chosen to keep every original, in a table of its own, for the local use, so that a later model or a zoom could read more pixels.

Is a database of terabytes still fine?

For the local file, SQLite itself is fine. Its limit is about 17 TB with the default page size, and a lookup by key takes a few more page reads as the file grows, not many more. What gets slow is each operation that touches the whole file:

  • A backup copies every byte.
  • A change that copies a large table needs hours and twice the disk space. The local file is never migrated (section 1), so this is the cost of a change on the server.
  • A full check (pragma integrity_check) reads everything.

The schema guards against these: no new kind needs a copy of everchat_msg (the everchat_kind table), and the large bytes are in their own table (everchat_image), so the other tables stay small and fast to scan. Text alone will not come near a terabyte. If a seat logs 20 MB of text a day, a year is about 7 GB. Only images can reach a terabyte, and each is at most 5 MB, as sent [Q44].

Should pick be normalized?

Yes. It was on each turn as text, and on each usage row as four text columns, and there is about one usage row per message. It is now the table everchat_pick.

Times on every row, and the five questions

Every row of data has created. I push back on one point: updated on a row that can never change. On everchat_msg, everchat_node, everchat_usage and the like, it would always equal created. It would take space, and it would suggest that the row can change. The schema says the opposite, and enforces it (section 1). Rows that do change have updated or ended.

The five questions are answered by references, with no extra columns. For a message:

Several independent chats in one database?

Yes, now. Draft 2 said no: one database per chat. The design for many chats settles it the other way [Q2, Q3, Q15, Q16]: a hosted deployment holds up to 100,000 chats of many tenants in one MariaDB schema, and one schema for all builds puts the keys for many chats in the local file too. Draft 2's reasons, and what answers each now:

  • The spirit of the original: one chat that never ends, per person. The local use keeps it: one home, one file, one chat. A hosted person can have many chats [Q19].
  • One writer: one process for each local file; on a server, one active process for each deployment, with a lease [Q22].
  • Backup, move, delete: the local chat is still one file. On a server, the product's backups of the schema include the chats [Q47], and a delete of a tenant cascades to its chats and their rows.
  • Simple keys: every key of a chat's table has the chat in front, and node (l, i) is (chat, l, i). Each reference carries the chat, so the keys are also the tenant boundary (section 1).
  • Damage stays small: only code keeps tenants apart on a server, and the owner accepted that risk; a tenant that needs full isolation gets a deployment of its own [Q5, Q8, Q13].

A program that wants to read across local chats can open several files in one connection (ATTACH).

Could a subagent need its own process?

Not for speed. An agent waits on model calls and on shells, and those already run outside the program's one thread. A separate process would also break two things: the one-writer rule, and the factory's rule that each shell is a direct child of the runtime. So subagents stay in the process. If one ever needs its own process, it must not open the database: it sends its events to the owner, which writes them. And an agent that must be truly independent is a second EverChat with its own home, which is what a seat is.
