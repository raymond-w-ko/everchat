EverChat schema draft

The tables of the one SQLite database that holds almost all of EverChat's state. Draft 2, for review, before any code.

This page follows docs/state.md, which lists the 63 pieces of state that the old code keeps. The goals are in AGENTS.md, "All state in one SQLite file". Draft 2 also checks the design against the factory's seat runtime interface (everturn ADR 0186 and packages/bridge/src/runtime/types.ts).

The words on this page are those of GLOSSARY.md.

Decided already:

  • The driver is @effect/sql-sqlite-bun (Effect's SQL client over bun:sqlite). Bun bundles SQLite 3.53.4.
  • synchronous = full: each commit is on the disk before the call returns. We will revisit this if it feels too slow.
  • Greenfield: no old chats, and no migration from the old files.
  • Model calls go through the author's inference gateway, with an API key, for both OpenAI and Anthropic. The sign-in with a ChatGPT plan is for later. Its tokens will then go in the database.
  • Imports of old Claude Code and Codex sessions are out of scope. Their tables and the imported flag are gone.
  • The kind of EverChat's own messages is asst (section 12).
  • Version 1 deletes nothing: every turn's items and every call's whole output stay in the database, so that they can be measured. Deleting is a question for version 2.
  • Background shells are for version 2. Version 1's background work is a subagent. EverChat has two uses. In the factory, it is a chief of staff that hands coding work to mature harnesses (Claude Code, Codex). Alone, for example as a person's main assistant, it has no other harness, and it uses its own subagents a lot. So subagents must be cheap and solid.
  • OpenAI goes first, then Anthropic.

What changed from draft 1

  • New: chat (one row, typed columns) replaces the key and value table state. launch (one row per start of the program) replaces the owner and run_tag keys.
  • New: kind and pick are small tables, and other tables point to them with a small number.
  • New: head keeps the system prompt and the tool list of a turn, as sent.
  • Merged: tool_call and the "later" tool_step are now one table, call. The factory's interface needs each shell command, so it cannot wait.
  • Removed: the hook outbox hook_event. Section 9 says why.
  • Times are integers now. Every row has created. Section 1 gives the rule for updated.

1. Rules for every table

  • One home, one database, one chat. EverChat has one chat that never ends. The variable EVERCHAT_HOME names a directory (the home), and the database is one file in it. A second, independent chat is a second home. The table chat has exactly one row.
  • One writer. One process owns the file. The table launch shows which. Other programs may read the file (WAL mode allows that), for example a backup.
  • One event, one transaction. Each event (a message sent, a step done, a function started) writes all its rows in one transaction. After a crash, an event is there whole or not at all. Section 7 lists the events.
  • Append only where the memory needs it. A message's id never changes and is never reused. The tree math depends on it (node (l, i) covers messages i·2^l on). The tables msg, agent_msg, node, turn_item and usage have triggers that refuse an update. msg, agent_msg and node also refuse a delete. A bug in the program then cannot rewrite the chat's history.
  • Times are integers: milliseconds since 1970-01-01 UTC. An integer takes 6 bytes, and the ISO 8601 text of draft 1 took 24. The program formats a time when it shows it to the model or to a person.
  • Order comes from ids, never from times. A clock can jump back, and a chat can move to another host. Times are for people.
  • created and updated. Every row of data has created. A row that can change also has the time of its last change: updated, or ended for a row that changes only once, when it closes (a turn, a call, a launch). A row that can never change has no updated. That absence is a statement: the triggers above enforce it.
  • Who, what, when, where, why come from the structure, not from five more columns on each row. Section 12 has the table.
  • Small numbers for repeated values. A value that repeats on many rows of a large table, and whose list can grow, is a small integer that points to a small table (kind, pick). SQLite cannot change a check list without a copy of the whole table, so a list in a small table is the only cheap way to add a value later. A status on a small table stays a word with a check, because it is easy to read.
  • STRICT tables. SQLite then checks each column's type.
  • Well-formed text. SQLite writes a lone surrogate as U+FFFD. So the program makes every string well formed (toWellFormed()) before it uses it, and the text in memory always equals the text on disk. size is the length of that text in UTF-8 bytes.
  • Flags are integer not null default 0, checked to be 0 or 1.
  • JSON goes in text columns, and only for values that the program always reads and writes whole (a view's parts, a vendor item). Anything the program searches or joins on gets its own column.
  • Migrations run through Effect's migrator, loaded with Migrator.fromRecord, so they are compiled into the executable. The migrator keeps its own table (effect_sql_migrations). Each migration has a test that runs it on an empty database and on the one before it.
  • Pragmas at open: journal_mode = wal (the driver sets it), synchronous = full, foreign_keys = on. The driver waits up to 5 s on a locked file and starts each write with BEGIN IMMEDIATE.

3. The chat and its launches

chat

The chat itself (items 11, 38, 43). It has exactly one row, so "one database, one chat" is a fact that the database checks. Draft 1 had a table of keys and JSON values. Typed columns are better: SQLite checks each type, the pick is a real reference, and a new value is one alter table add column.

create table chat (
  id      integer primary key check (id = 1),     -- exactly one row
  uuid    text    not null,                       -- made once, never changed
  pick    integer not null references pick (id),  -- the next turn's pick
  goal    text,                                   -- the /goal text, or null
  draft   text,                                   -- typed and not yet sent
  taken   integer not null default -1,            -- the last message that a request has taken in
  created integer not null,
  updated integer not null
) strict;

taken answers "which messages wait for a turn?" after a restart: the user and work messages with a higher id. A message that comes while a turn runs is logged at once, but the turn takes it in only after its step's results. The old code kept this in memory only.

uuid is the chat's id for the world outside. The factory calls it the session id, and it must be the same at every launch (ADR 0186, rule 3).

launch

One row for each start of the program (items 31, 60). It does four jobs:

  • Owner. A launch with no ended is live, or it crashed. The index below lets at most one such row exist. A new start checks whether that process still runs. If it does, the new start stops. If not, it closes the old row with why = 'crash' and adds its own, in one transaction. A launch that ends in order writes its own why: exit, signal (it was interrupted), or error (it failed, and still closed the file).
  • Leftover shells. Each shell gets the launch's run_tag in its environment. The next start stops each process that still carries an old tag.
  • Where. Other rows point to the launch that wrote them. That gives the host, the directory and the program's version for every message, without three columns on each row.
  • The factory's session record. ADR 0186 keeps one record per launch of a continuous chat. This table is that record.
create table launch (
  id      integer primary key,
  pid     integer not null,
  host    text    not null,
  cwd     text    not null,                 -- the work directory
  version text    not null,                 -- the program's version
  run_tag text    not null,                 -- marks the shells this launch starts
  pick    integer references pick (id),     -- given on the command line, or null
  created integer not null,                 -- when it started
  ended   integer,                          -- null: it runs, or it crashed
  why     text                              -- exit, signal, error, crash
) strict;
create unique index launch_live on launch ((1)) where ended is null;

The factory sets the model and the effort on the command line (its requirement R2). So a launch can carry a pick. The pick of the next turn is the launch's, if it has one, or else the chat's.

4. The log

kind

The kinds of message. The name is the word the model reads before each message (user: ...), as in the old code (Memory.show). A new kind is one new row, with no copy of msg. A test checks that this list equals the list in the code.

create table kind (
  id   integer primary key,
  name text    not null unique
) strict;
insert into kind (id, name) values
  (1, 'user'),   -- the person
  (2, 'asst'),   -- EverChat's reply ("assistant"; the old code says 'ever')
  (3, 'tool'),   -- a program the model ran
  (4, 'echo'),   -- that program's result
  (5, 'work'),   -- an agent's report
  (6, 'note');   -- a note from the program itself

mind (a thought) is not a kind here: thoughts are shown and never logged, as before.

msg

The chat's log (item 1). One row per page. A long message is cut into pages, and more = 1 says that the message continues in the next row. All pages of a message are written in one transaction, so a crash can no longer leave a message half written.

create table msg (
  i       integer primary key,              -- message id: 0, 1, 2, ... never reused
  kind    integer not null references kind (id),
  text    text    not null,                 -- well formed
  size    integer not null,                 -- UTF-8 bytes of text
  more    integer not null default 0 check (more in (0, 1)),
  line    text,                             -- its own summary line, when the writer gives one
  turn    integer references turn (id),     -- the turn that wrote it, or that it started
  call    integer references call (id),     -- tool and echo: the program they belong to
  launch  integer not null references launch (id),
  created integer not null
) strict;
create trigger msg_no_update before update on msg
  begin select raise(abort, 'msg is append only'); end;
create trigger msg_no_delete before delete on msg
  begin select raise(abort, 'msg is append only'); end;

msg_image

The images of a message, in order. Draft 1 had a JSON list in msg. A table gives a real reference: a message cannot name an image that is not there.

create table msg_image (
  msg   integer not null references msg (i),
  n     integer not null,                   -- 0, 1, 2, ... in the message
  image integer not null references image (id),
  primary key (msg, n)
) strict, without rowid;

It has no time of its own. It is written with its message and never changes, so the message's created is its time.

node

The tree of summaries (item 3). Node (l, i) is one line of at most about 512 bytes that covers the 2^l messages from i·2^l on. All levels are in this one table. Section 12 says why, with a measurement.

create table node (
  l       integer not null check (l >= 0),
  i       integer not null check (i >= 0),
  text    text    not null,
  size    integer not null,
  created integer not null,
  primary key (l, i)
) strict, without rowid;
create trigger node_no_update before update on node
  begin select raise(abort, 'node is written once'); end;
create trigger node_no_delete before delete on node
  begin select raise(abort, 'node is written once'); end;

A node is written once. A second write of the same node is a bug, and the primary key makes it fail. Which model made a node is in usage. A node whose source was short enough has no usage row: the old code builds it with no request (Memory.pump).

view

The two views (items 5, 6): the chat's (for turns) and the compactions' (seen in the code). A view must come back byte for byte after a restart. If it does not, the first call after the restart misses the vendor's cache, which is mistake 3 of optchat.md. It is always read and written whole, so its parts are one JSON value and not rows.

create table view (
  name    text    primary key check (name in ('chat', 'seen')),
  parts   text    not null,                 -- JSON [[l, i], ...], oldest first
  batch   integer not null default 0 check (batch in (0, 1)),   -- a merge is under way
  created integer not null,
  updated integer not null
) strict, without rowid;

A view changes when a merge is accepted (Memory.fit). That write goes in the same transaction as the nodes that made the merge possible.

image and image_original

The images that messages carry (item 15). Decided: every original is kept. An image is two tables:

  • image holds the bytes as sent to the model. Each request with the image reads this row.
  • image_original holds the original, and only when it is not what was sent (it was too large, so the model got a scaled JPEG of at most 1568 px). Almost nothing reads this row.
create table image (
  id      integer primary key,
  name    text    not null unique,          -- as the model reads it: 16 hex digits of the original's SHA-256, and its type
  type    text    not null,                 -- MIME type of bytes
  width   integer not null,                 -- of bytes, in pixels
  height  integer not null,
  source  text    not null check (source in ('person', 'tool')),
  created integer not null,
  bytes   blob    not null                  -- as sent to the model
) strict;

create table image_original (
  image   integer primary key references image (id),
  type    text    not null,
  width   integer not null,
  height  integer not null,
  bytes   blob    not null
) strict;

Why two tables, and not two columns:

  • The sent bytes must be stored, not made again. A different JPEG encoder would give other bytes, and the request's prefix would no longer match the vendor's cache.
  • The hot rows stay small. SQLite stores a row's columns one after the other. With both in one row, a read of the sent bytes would first pass over the pages of a large original.
  • An image that was sent as it is has one copy, and no row in image_original.
  • The originals can move. If they grow too large for one file, this one table can go to a second database file. No other table points to it.
  • The originals can be dropped, as a last resort. If space runs out, the rows of very old images can be deleted from image_original. Nothing breaks: the chat, the memory and every request use image only. The owner strongly prefers not to do this, so the program never does it by itself. It needs a command that a person runs, and moving the table to a second file comes first.

image_original has no time of its own: it is written with its image row and never changes. The blob is the last column of each table, so a read of the other columns does not touch it.

5. Work

A turn is one agent loop: a first message, then steps and programs, until a step that runs no program. The chat has turns, and so does each agent. The old code kept a running turn only in memory (items 13, 22). After a crash, the new turn got only a restart note.

pick

A pick is a model choice: vendor, model, effort and speed. Draft 1 wrote it as text on each turn, and as four text columns on each usage row. There is about one usage row per message, because each compaction is a request. So the pick is now one row here, and the other tables hold its number.

create table pick (
  id      integer primary key,
  vendor  text    not null,
  model   text    not null,
  effort  text    not null,
  speed   text    not null,
  created integer not null,
  unique (vendor, model, effort, speed)
) strict;

head

The head of a request is the part before the messages: the system prompt and the tool list. A turn that continues after a restart must send the same head as before. The program may be a newer version by then, with a changed prompt. So each head that is sent is kept, once, and found by its hash. Thousands of turns share one row.

create table head (
  id      integer primary key,
  hash    text    not null unique,          -- SHA-256 of body
  body    text    not null,                 -- JSON: the system prompt and the tool list, as sent
  created integer not null
) strict;

This also gives the cache rule in askai.ts the fact it lacks today: two requests can share a cache prefix only if they have the same head (docs/api-audit.md, A3).

turn

create table turn (
  id        integer primary key,
  agent     integer references agent (id),  -- null: the chat's own turn
  status    text    not null check (status in ('running', 'done', 'stopped', 'failed')),
  pick      integer not null references pick (id),   -- fixed for the whole turn
  head      integer not null references head (id),   -- fixed for the whole turn
  first_msg integer not null,               -- the message that started it: msg.i, or agent_msg.i for an agent
  launch    integer not null references launch (id), -- the launch that started it
  created   integer not null,
  ended     integer,
  why       text,                           -- stopped or failed: why
  check ((status = 'running') = (ended is null))
) strict;
create index turn_running on turn (status) where status = 'running';

At start, a turn with status running was cut. The pick stays with the turn, because the turn must continue on the same model: Anthropic's thinking blocks are bound to the model that made them. stopped means that the person stopped it. failed has the vendor's error text in why. The factory's turn-end event needs both.

turn_item

The request of a turn, step by step (item 23): item 0 is the first user message exactly as sent (the view's blocks, the devices, the user's text), then each model output, then each batch of tool results. This is what lets a restart continue inside the cut turn:

  • Item 0 holds the view as it was when the turn started. The view may have changed since, but the request is byte for byte the old one. So it reads the vendor's cache.
  • The request stays append only, which Anthropic's history check needs (docs/api-audit.md, "Append only within a turn").
  • The vendor's own items (reasoning, signatures, encrypted content) are kept as received, so they go back unchanged.
create table turn_item (
  turn    integer not null references turn (id),
  n       integer not null,                 -- 0, 1, 2, ... in request order
  kind    text    not null check (kind in ('user', 'turn', 'back')),
  body    text    not null,                 -- JSON: our Item, the vendor's output inside as received
  created integer not null,
  primary key (turn, n)
) strict;
create trigger turn_item_no_update before update on turn_item
  begin select raise(abort, 'turn_item is append only'); end;

Images in an item are kept as image names, not as base64. Decided: version 1 keeps the items of every turn, with no limit. They are the only record of what the model was really sent, so they are what cache and cost measurements need; the leaves alone would lose that. Item 0 can be 100 KB or more, so a thousand turns are about 100 MB. Version 2 may delete old items, which is why this table refuses an update but allows a delete.

call

Code mode is the only primary tool. So what the model runs is a program, and the program calls functions (shell, read, write, edit, zoom). Both are a call, and both are rows here, written when they start (items 25, 30, 31):

  • A row with no parent is a program that the model ran. fn is run, and input is the program's source.
  • A row with a parent is one function that the program called. input is its arguments, and output is what it gave back.
create table call (
  id        integer primary key,
  turn      integer not null references turn (id),
  parent    integer references call (id),   -- null: the model's own call
  vendor_id text,                           -- the vendor's call id: only on the model's own call
  fn        text    not null,               -- run, shell, read, write, edit, zoom, ...
  input     text    not null,               -- the program's source, or the function's arguments as JSON
  output    text,                           -- the whole result, as produced
  size      integer,                        -- UTF-8 bytes of the result
  shown     integer,                        -- bytes of it that its reader got: less than size when it was shortened
  status    text    not null check (status in ('running', 'done', 'failed', 'denied', 'cut')),
  pgid      integer,                        -- shell: its process group, while it runs
  launch    integer not null references launch (id),
  created   integer not null,
  ended     integer,
  check ((parent is null) = (vendor_id is not null)),
  check ((status = 'running') = (ended is null))
) strict;
create unique index call_vendor  on call (turn, vendor_id) where vendor_id is not null;
create index        call_parent  on call (parent)          where parent is not null;
create index        call_running on call (status)          where status = 'running';
  • The old code logged a call only when its result came. A crash after a tool ran left no trace that it wrote a file or ran a command. Now a restart reads the open rows and tells the model exactly which functions ran, and which one was cut.
  • The memory still gets a program and its result as two msg rows (tool, then echo), as before. The functions inside do not go in the log. They are a record, not memory.
  • denied is for a function that a hook refused (section 9).
  • output is always the whole result, for a program and for a function. What the model was shown can be less: see "The output limit" below.
  • The factory's interface asks for exactly these two levels: each shell command as one call with its command and its output, and each program as a call of its own kind (ADR 0186, rule 4).

The output limit

Decided: the database keeps a result whole, and the model is shown a limited form. Three things happen when a program's result is over the limit:

  1. The model gets the head and the tail, with a line between them that says how much was left out and where the whole text is. The echo message in the log is this limited text, so the memory holds what the model saw.
  2. The amount is recorded: size is what was produced, and shown is what the model got.
  3. The whole text is written to a file in a private directory under the system's temporary directory (/tmp), named after the call's id. The model can read or search it with its normal functions. The file is a copy, not state. If it is gone (after a reboot, for example), a function writes it again from call.output.

The default limit is 30,000 characters, set in the config file. Three sources agree on about that size:

HarnessShown to the modelThe rest
The old code (clip.ts, CAP)30,000 characters: the head and the tail, half eachLost. A line says how many characters were cut
Claude Code (its tools reference)About 30,000 characters. A failed command: about 10,000, head and tailA file in the session directory, with a preview of the first 2,000 characters. Settable up to 128,000
Codex (tool_output_token_limit)10,000 tokens by reports, which is about 30,000 to 40,000 characters. The official page gives no numberHead and tail kept, with a warning

Two points come from code mode:

  • The limit is on what the model reads, not on what a program gets. A function gives its whole result to the program that called it, so the program can search or parse it. The limit applies to the program's own result, which is what goes to the model.
  • A second, hard limit is still needed. A command that never stops printing must not fill the memory or the database, and SQLite cannot store a text over 1 GB. Decided: 64 MiB, the size at which Claude Code cuts its saved file. Past it, the output ends there and the command is stopped. size still tells the true amount.

agent and agent_msg

Each subagent or computer task (items 17, 18, 28). The old code kept an agent's role and effort only as words in its first log note, and parsed them back. Its replies and its stop flag were in memory only.

create table agent (
  id      integer primary key,
  name    text    not null unique,          -- random AdjNoun; also the name of its work directory
  role    text    not null check (role in ('sub', 'hands')),
  effort  text,                             -- sub: its own effort, or null for the configured one
  device  text,                             -- hands: the device it works on
  turn    integer references turn (id),     -- the chat turn that started it
  task    integer,                          -- agent_msg.i of the message that began its present task; null: idle
  taken   integer not null default -1,      -- the last message of its log that a request has taken in
  stop    integer not null default 0 check (stop in (0, 1)),   -- the present task was stopped
  view    text,                             -- sub: JSON, the chat view's parts for its present task
  created integer not null,
  updated integer not null,
  check ((role = 'hands') = (device is not null))
) strict;

create table agent_msg (
  agent   integer not null references agent (id),
  i       integer not null,                 -- 0, 1, 2, ... per agent
  kind    integer not null references kind (id),
  text    text    not null,
  size    integer not null,
  turn    integer references turn (id),
  call    integer references call (id),
  created integer not null,
  primary key (agent, i)
) strict;
create trigger agent_msg_no_update before update on agent_msg
  begin select raise(abort, 'agent_msg is append only'); end;
create trigger agent_msg_no_delete before delete on agent_msg
  begin select raise(abort, 'agent_msg is append only'); end;

An agent's log is a plain list with no tree, as in the old code (Memory.agent_push takes a kind and a text). It stays apart from msg, because the ids of msg are the tree's coordinates and must be 0, 1, 2, ... with no gap.

A task is an agent's work from one message to its report. It can take more than one turn: a message that came too late for a turn starts the next one. The columns follow the old code (Tools.start, Tools.tell, Tools.run, Tools.ask):

  • No pick. An agent has no model of its own. Each turn runs on the configured agents' pick, or else the chat's pick at that time, with the agent's own effort if it has one. The pick that ran is on the turn. An agent with no effort of its own, on the chat's pick, reads the chat's cache.
  • view is taken anew for each task, and every turn of the task uses it, so they share one cache prefix. Agents started together get the same view, so they share it too. A computer task has no view.
  • An agent does not read the chat's own cache in the old code. It gets the same view, but its system prompt is another one (SUB, not MASTER), and the system prompt comes before the view in a request. Its pick can differ too. So an agent's first request pays for the whole view at the full price. The cache rule knows this: AskAI.keys starts from the pick and the system prompt. The new code changes this: see "One system prompt" below.
  • task marks where the present task began. The report is the last reply of each turn since then, or "failed" and the reason. So a restart can still build it. An agent with no task is idle.
  • stop: a stopped task still reports, but its report starts no turn in the chat.

The spirit. In the original, the chat is the only memory. An agent is a short side chat: its whole log goes in each request, it has no tree, and what it found enters the memory as one work message. The schema keeps all of that. One assumption needs a check during the port: view holds the view's parts and not its text. That is exact only if every node of the view is built when the view is taken (Memory.settle waits for that) and the text of a part never changes after.

One system prompt for the chat and its subagents (decided)

Today a subagent has its own system prompt, so it cannot read the chat's cache and pays for the whole view again (section 5). Decided: a subagent gets the chat's system prompt, and a message after the view tells it that it is a subagent.

The old code already does this for compactions. Its one system prompt says: "Each call to you is a turn or a compaction: the view below is followed by the user's new message, or by a task starting Compaction:." The rules for a compaction are a section of that prompt, and the text after the view chooses the role. A cheap compactor model follows it.

The design:

  1. One head. The chat and its subagents send the same system prompt and the same tool list. Code mode makes the tool list equal for free: there is one tool.
  2. The system prompt names three kinds of call: a turn, a compaction, and a subagent task. The rules for a subagent (today's SUB text) become a section of it, next to the compaction section.
  3. The request is: the head, the chat's view, the open devices, then a block that starts Subagent task: with the agent's name and its log. The first two parts are bytes that the chat already sent, so the agent reads them from the cache.
  4. Code enforces what a subagent may do, not the prompt. A subagent's program that calls a function only the chat may use (to start an agent, for example) gets an error.
  5. The pick is a choice per agent. On the chat's pick, the agent reads the chat's cache. On a cheaper model or another effort, it has its own cache, as today, but still the same prompt.

Is a message strong enough? Yes, if the system prompt itself defines the mode. Then the message does not argue with the system prompt ("you are EverChat" against "you are a subagent"). It starts a mode that the system prompt describes, and it is the last thing the model reads before it acts. Three sentences of today's subagent prompt must stay in that last block, because they guard against the known mistakes: do the task and not what the user's last message says; the final reply is a report to EverChat and not to the user; the view is context only.

What it saves. A view is 64 to 128 KB. Today each group of agents that start together pays for it once at the full price, and so does each new task for an idle agent. With one head, they read it from the cache. A computer task gains nothing: it has no view, and it has another tool.

For the schema: no change. An agent's turn points to the same head row as the chat's turns.

8. What a restart does

  1. Take the file. Open it and run the migrations. Read the launch row with no ended. If its process still runs on this host, stop. If not, close it with why = 'crash' and add our own row.
  2. Clean up processes. Stop each process that still carries the run_tag of a launch that ended (a shell that a crash left running).
  3. Load the memory. Read both views from view, byte for byte. Read the nodes that they and the tree above them need. Find the nodes to build with a query (nodes not built whose two halves are), not with a walk of the tree.
  4. Close the cut calls. Set each call still running to cut. For a cut program, log its tool and an echo that lists its functions: which ended, with what result, and which one was cut ("It may or may not have finished."). Add the same text as its result in the turn's items.
  5. Continue the cut turns. For each turn still running (the chat's and each agent's), build the request again from its head and its turn_item rows, and send the next step. The prefix is the one sent before, on the same pick. So it reads the vendor's cache and keeps the thinking blocks valid.
  6. Start the compactions again. Their state is derived, so nothing is stored for them. A compaction that was cut is asked again.

ADR 0186 expects step 5: "a continuous chat resumes with the cut turn at its next launch" (rule 3).

9. Hooks, and why the outbox is gone

Draft 1 had a table hook_event: an outbox that kept each event until a hook had run for it, also after a crash. ADR 0186 shows that this is the wrong shape for the factory, for three reasons:

  • A hook speaks about the live process. The bridge accepts a hook's event only from a direct child of the runtime process that runs now. An event of a process that died, sent late by the next process, would describe a state that is gone. When EverChat dies, the bridge sees the exit itself.
  • A hook can answer. The session-start hook gives text for the model. The hook before a shell command can refuse it. The hook after a program can add text for the model (the factory's "steer mail"). So EverChat must wait for each hook, at the point where it runs.
  • What must last is the answer's effect, not the event. That effect already has a place: text for the model becomes a msg row and a turn_item, and a refusal becomes a call with status denied and the reason as its output.

So there is no hook table now. Hooks come later, and section 7 marks the points where they will run. The puzzle "how do shell hooks work when the only tool is code mode" has an answer in the ADR (rule 4), which Codex's code mode already follows:

  • The hook before a tool runs for each shell command, not for the program around it. It runs in the shell function on the host side, before the command starts. The hook sees the command text.
  • The hook after a tool runs after each program.
  • The sandbox must have no other way to start a process, and no way to type into a command that already runs. Without both, a command could pass the hook unseen. This is a condition on the code-mode design (how pi-codemode runs a program), not on the schema.
  • Each command's shell must be a direct child of the EverChat process, wherever the sandbox runs.

The transcript: a JSONL export (decided)

The interface wants a file of JSON lines that the bridge can follow, and our state is a SQLite file. So EverChat also writes a JSONL file, as an export. The database stays the only state: EverChat never reads the file back, and a deleted file loses nothing.

The file is append only. A line is written once, after its transaction is on disk, and it never changes. The bridge needs this: it remembers a byte position in the file and reads only what comes after. The rule for what gets a line follows from section 2:

  • A row that never changes gets one line (a message, a model request's usage).
  • A row that changes once, when it closes, gets two lines: one at its start and one at its end (a launch, a turn, a call). A reader joins them by id. A call with a start line and no end line is still running, or was cut.
  • A row that changes often, or that is derived, gets no line.

It holds what happened, in full, and not the memory. The tree's nodes and the views are not in it.

One file per launch. Each launch writes its own file, named after its launch row. A file ends with its launch, so the factory's archive can call it done, and a person can delete old files with no loss. One file for the whole chat would never end and would grow as large as the chat. ADR 0186 assumes one file for a continuous chat ("each names the same transcript"), so the adapter's ADR must change that sentence.

After a crash, some rows can be in the database and not yet in the file. Each line carries its row's id, so the next start reads the end of the crashed launch's file, finds the last id of each kind, and adds what is missing there, before it starts its own file. Lines of one kind are always in id order.

Section 12's five questions hold in the file too: each line has its time, its launch, its turn and its call.

What tells the factory that a typed line was accepted (decided)

For EverChat, a turn is one loop: from a first message until a step that calls no tool. For the bridge, a turn start is also the proof that the line it typed was taken: send answers "accepted" at the next turn start, and "refused" after a timeout. The two agree when a message comes to an idle chat. They differ in three cases:

  • A message while a turn runs. It steers the running turn: the model reads it between two programs, as in the old code. No turn starts, so the bridge would answer "refused" for a line that was taken.
  • A message too late for the running turn. It starts the next turn by itself when the running one ends. A turn starts, but later than the bridge's timeout may allow.
  • A turn that continues after a restart. It starts with no message at all, right after the session start.

Decided, with no change to the interface: EverChat has its own event "a message was accepted", sent when the message is in the log (at once, on Enter), and its own turn events. The adapter turns the accepted event and each turn start, also one that continues after a restart, into the bridge's turn start, with the turn's id. One check is left for the adapter's ADR: that the bridge takes a second turn start inside a running turn.

12. Answers to the review questions

The word in place of "unii": asst (decided)

The table stores the number 2, and the word is one row in kind. But the word matters, because the model reads it before each of its own messages (asst: ...), and the compactor writes it inside summaries. The old code says ever, which is an English word: a summary can read oddly, and a search also finds "every" and "never". asst is the standard short form of "assistant", so a person and a model both read it right with no definition.

It has 4 letters on purpose. The prefix counts toward a node's 512 bytes (Memory.show), so asst: keeps the byte budgets of upstream's unii: : a message is its own leaf, with no request, up to 506 bytes of text. A longer word breaks nothing, but it sends a few more messages to the compactor. The new code uses asst from the start. The old code keeps ever until it moves to ref/, and the ported tests change only that word.

Should kind be a number?

Yes, but not for the space. The word takes about 4 bytes more than the number, on rows of hundreds of bytes: under 1%. The real reason is growth. SQLite cannot change a check (kind in (...)) list without a copy of the whole table. For msg, the table that grows forever, that copy is the one thing to avoid. With the small table, a new kind is one new row. Statuses on small tables stay words.

All levels of node in one table, or a table per level?

One table. A table per level is a bad idea:

  • The set of tables would grow while the program runs. A migration cannot describe that, and each query needs a table name built at run time.
  • It gains nothing. With the key (l, i), SQLite already keeps each level together on disk, in order of i.
  • A query across levels becomes impossible. The restart needs one: "the nodes not built whose two halves are".

There are few levels: a million messages make 20. I measured three shapes of this one table, with 800,000 nodes of 200 to 512 bytes:

ShapeFileOne random readOne read in a run at one level
Key (l, i), without rowid (this draft)305 MB9.0 µs3.8 µs
Key (l, i), ordinary table311 MB8.7 µs5.6 µs
One integer key, the old code's Memory.slot326 MB6.2 µs5.2 µs

All three are fast, and they differ by microseconds, next to requests that take seconds. So the draft keeps the plainest shape. The reads used a 2 MB page cache and a warm disk cache. All 800,000 rows took 2.5 to 3.3 s to write, in batches, without synchronous = full.

Keep the original image? Yes, all of them (decided)

The log is forever, and the scaled JPEG loses detail. A later model may read more pixels, and the agent could zoom into a part of the original, which is EverChat's own idea applied to images. The cost is space: a computer task can make a screenshot at each step, and a thousand screenshots of 2 MB are 2 GB a day. So the originals have their own table, image_original (section 4). They are out of the way of every read that a request makes, and they are the one table that can move to a second file. An image has a row there only when the original is not what was sent, so no byte is stored twice. As a last resort for space, the rows of very old images can be deleted, but only by a person's command (section 4).

Is a database of terabytes still fine?

SQLite itself is fine. Its limit is about 17 TB with the default page size, and a lookup by key takes a few more page reads as the file grows, not many more. What gets slow is each operation that touches the whole file:

  • A backup copies every byte.
  • A migration that copies a large table needs hours and twice the disk space.
  • A full check (pragma integrity_check) reads everything.

The schema guards against these: no migration needs a copy of msg (the kind table), and the large bytes are in their own tables (image, image_original), so the other tables stay small and fast to scan. Text alone will not come near a terabyte. If a seat logs 20 MB of text a day, a year is about 7 GB. Only images can reach a terabyte, and of those, the originals are the large part. If they ever grow too large, image_original can move to a second database file with no change to the other tables.

Should pick be normalized?

Yes. It was on each turn as text, and on each usage row as four text columns, and there is about one usage row per message. It is now the table pick.

Times on every row, and the five questions

Every row of data has created. I push back on one point: updated on a row that can never change. On msg, node, usage and the like, it would always equal created. It would take space, and it would suggest that the row can change. The draft says the opposite, and enforces it with triggers. Rows that do change have updated or ended.

The five questions are answered by references, with no extra columns. For a message:

QuestionAnswer
Whokind: the person, EverChat, a program, an agent, the program itself. For EverChat's own words, the model is turn.pick
Whattext, and its images

Wherelaunch: host, work directory, process, program version

The same holds for a summary (usage names the model that made it), a call (its turn, its parent, its launch) and a turn (its first message, its pick, its launch).

Several independent chats in one database?

No. One database per chat, and one home per database, as you suggest with the variable. It also fits the factory, which gives each seat its own config root. Reasons:

  • The spirit of the original. One chat that never ends, per person. The old server kept many people's chats, but each in its own files.
  • One writer. SQLite allows one writer per file. Several processes on one file would wait on each other at every commit.
  • Backup, move, delete. One chat is one file. To remove a seat is to remove its home.
  • Simple keys. With several chats, every key needs a chat column, and node (l, i) becomes (chat, l, i).
  • Damage stays small. A broken file breaks one chat.

A program that wants to read across chats can open several files in one connection (ATTACH).

Could a subagent need its own process?

Not for speed. An agent waits on model calls and on shells, and those already run outside the program's one thread. A separate process would also break two things: the one-writer rule, and the factory's rule that each shell is a direct child of the runtime. So subagents stay in the process. If one ever needs its own process, it must not open the database: it sends its events to the owner, which writes them. And an agent that must be truly independent is a second EverChat with its own home, which is what a seat is.
