How EverChat remembers: a masterclass

The memory system as the code really runs it: the log, the tree of summaries, the view, the requests and their cache marks, how a turn's transcript is folded into the tree, and the mistakes that are easy to make.

This document explains the memory system as the code really runs it. It starts from optchat.md, the upstream design note, and goes deeper. It shows:

  1. how a message becomes a leaf, and how leaves become a tree;
  2. how the view (the slice of the tree that a call sees) grows and shrinks;
  3. what an LLM request looks like, block by block, and where the cache marks sit;
  4. how that request changes state: inside one turn it is a normal transcript, and after the turn the transcript is folded into leaves of the tree;
  5. the mistakes that are easy to make here, and how the code avoids them.

When this document and the code disagree, the code is right. Each section names the functions to read, as file and Namespace.function.

Note

Sizes are UTF-8 bytes, never tokens, unless a line says otherwise. The facts here about the vendors' cache rules come from the comments in src/anthropic.ts, src/openai.ts, and optchat.md. Check the vendor's own docs before you change where the marks go.

0. Terms

Term Meaning
message One logged entry, with a permanent id i. A user's words, a reply, a tool call, a tool result, a report, or a note.
kind The type of a message: user, ever (EverChat's replies), tool (a tool call), echo (a tool result), work (a subagent's report), note. mind (a thought) is shown but never logged. ai is how an imported chat's AI is labelled. src/askai.ts Kind.
page A message too long for one piece (more than CAP = 30,000 characters, src/clip.ts) is logged as several messages in a row. Each one is a page.
node (l, i) A line of the tree. Level l, index i. It covers the 2^l messages from i·2^l on.
leaf A node at level 0: one message in at most 512 bytes.
merge A node at level 1 or above: its two halves in at most 512 bytes.
ref id+n How the model names a node: its first message and how many it covers. (3, 5) is 40+8. Memory.ref.
compaction A model call that writes one node. Done by the compactor, a cheap model (config.COMPACTOR, by default claude-api:haiku-5.5:high:slow).
view A list of nodes that covers the chat from message 0 to the end, oldest first, with no gaps or overlaps.
turn The work that starts with a user message (or a report) and ends with EverChat's final reply. One turn is one call, and a call can have many steps.
step One request to the model and its streamed answer. A turn with 5 tool calls in a row has at least 6 steps. Agent.step.
block One text piece of a request, with a flag mark. src/askai.ts Block.
mark A cache breakpoint. The vendor stores a cache entry for the prefix that ends at a mark.
prefix Every byte of a request from its start up to some point. A cache entry serves a request only if the request starts with that exact prefix.
batch A rewrite of the view that merges many line pairs at once, to shrink it from its high mark to half. Memory.fit, Memory.merge.
fold (This document's word.) What happens to a turn's transcript after the turn: its messages are logged as leaves, and the next turn sees them only as lines of the view.

1. The big picture

There are two loops, and they run at the same time:

  • The turn loop talks to the user's chosen model. It sends the view, then the new message, and runs tools until the model stops.
  • The compaction loop runs in the background on the compactor. It turns every logged message into a leaf, then merges leaves in pairs, again and again.

The two meet in one place, Memory.settle. A turn does not start until every message before it is summarized. So a turn never sees a hole in its view.

2. The log: what is kept on disk

Read: src/memory.ts header comment, Memory.load, Memory.log, Memory.scan, Memory.place, Memory.read, Memory.save; src/disk.ts.

<chat dir>/
  main/YYYY-MM-DD.jsonl   messages: {i, kind, text, size, date, images?, imported?, line?, more?, act?}
  tree/YYYY-MM-DD.jsonl   nodes:    {l, i, text, size}
  main.index              16 bytes per message:  byte offset (f64) | day (u32) | length (u32)
  tree.index              16 bytes per node, at slot (2i+1)·2^l − 1
  view.json               both views as [l, i] pairs, plus pick, goal, work, how far each log is indexed
  docs/images/<hash>      images, by content hash (+ a .jpg copy scaled for models)
  docs/agent/<Name>.jsonl a subagent's own log

The rules:

  • Append only. A line is never edited or removed. Memory.append writes and Disk.wrote queues a flush. src/disk.ts flushes in groups (on Linux one syncfs per group), so no write waits on the disk, and an action is answered only after its flush.

  • Index by slot, not by search. main.index holds one 16-byte slot per message id. tree.index uses Memory.slot(l, i) = (2i+1)·2^l − 1. That formula is the in-order position of (l, i) in a full binary tree, so each node gets its own slot and the file never has to move.

    node (0,0) (1,0) (0,1) (2,0) (0,2) (1,1) (0,3) (3,0)
    slot 0 1 2 3 4 5 6 7

  • A crash leaves at most one bad line. Memory.scan skips a last line that has no newline, then appends the newline so the next write starts clean.

  • Pages wait for the last page. A long message is logged page by page (Memory.pages) with more: true on every page except the last. mem.count counts only finished messages, and mem.open counts the pages past it. Memory.load drops trailing more pages, because a crash in the middle of a paste must not leave half a message in the chat.

  • Thoughts are not logged. In Chat.on (src/server.ts) a mind entry goes to the screens only. A tool call is held back until its result comes, then both are logged together (tool, then echo), so they sit side by side in the tree.

3. The tree: leaves and merges

Read: Memory.source, Memory.store, Memory.ready, Memory.todo, Memory.roots, Memory.halves, Memory.span.

node(0, i) = message i, in at most 512 bytes
node(l, i) = node(l-1, 2i) + node(l-1, 2i+1), in at most 512 bytes

What the source of a node is

Memory.source(l, i) gives the text that the node must compress:

  • A leaf: the message's line if it was logged with one, else Memory.show(root), which is "<kind>: <text>" plus one [image docs/images/…] line per image. The kind goes inside the size. That is why the agent's kind is ever (4 bytes) and not a longer word: every byte of the kind is a byte the summary loses.
  • A merge: flat(a) + "\n" + flat(b), its two halves with their own newlines turned to spaces.

Free nodes

If the source fits in 512 bytes, the node is its source, with no model call (Memory.starts puts it in free, Memory.pump stores it). So:

  • a short message stays word for word;
  • two short lines are joined by a newline.

Most leaves of a chat are free: short replies, short user messages, small tool calls. Only long messages and long echoes need the compactor.

The tree is built eagerly

When a node is stored, Memory.store checks its sibling. If both are built and their parent is not, the parent goes into the ready queue. So every full pair gets merged, whether or not a view needs it yet. Each message costs at most about two compactions in its life: its leaf, plus its share of the merges above it (a binary tree has N − 1 merges for N leaves).

The roots

The tree is not one tree. It is a forest of perfect trees, one per 1 bit in the message count: Memory.roots(count). With 13 messages (binary 1101) the roots are 0+8, 8+4, and 12+1.

4. Compactions: how one node is built

Read: Memory.starts, Memory.job, Memory.build, Memory.ask, Memory.task, Memory.over, Memory.cut; the # Compactions part of src/prompt.txt.

When a node starts

  • Memory.ctx(l, i) is the message that the node's context reaches: i for a leaf (everything before it), and (i+1)·2^l for a merge (up to and including its last message).
  • Nodes start in message order. On a tie, the merge goes first (next.sort(... || b.l - a.l)).
  • There are two sides: 0 is the chat, and 1 is an import of old chats. Each side has its own queues and its own 64 jobs, and an import can be paused or held (mem.hold) without slowing the chat. A turn waits only on side 0 (Memory.settle uses Memory.first(mem), side 0).

What a compaction request holds

  • upto = min(ctx(l, i), first unbuilt leaf of this side). The view stops at the first line that is not built, so a compaction never sees a placeholder or half a message.
  • The view is the compactions' view (mem.seen, 16-32 KB), not the turns' view (mem.view, 64-128 KB). A summary needs enough context to resolve "that file" or "do it", not the whole chat.
  • A merge's view reaches up to its own last message, so the view may hold its messages in finer detail. The task says so: "<chat> may hold their messages, {id} to {end}, in more detail".

The retry loop

In words: an answer that fits is stored. One that is too long is asked again with a note, at most 5 tries in all, and the shortest is kept. If the vendor is down, the call waits 60 s and asks again. A refusal stores the source cut to 512 bytes. If the payer refuses, the node waits, with no calls, until there is credit.

Things to notice in Memory.build:

  • A retry is a fresh request, not a conversation. It sends the same blocks plus one note (Memory.over(line)): the size of the last try and its first 512 bytes, followed by | ← LIMIT. It never sends the model's earlier answer or thoughts. So the retry has the same prefix and reads it from the cache.
  • At most 5 tries, and the shortest line wins. A few bytes over 512 are fine, because the view counts real sizes.
  • An outage only delays. AskAI.ask with patient: true asks again every 60 s until it gets an answer (AGAIN in src/askai.ts). A node is never clipped because the vendor was down.
  • A refusal clips. If the model answers but fails (stop: "fail"), the node becomes its source cut to 512 bytes (Memory.cut(Memory.flat(text))). Asking again would fail the same way. Test: tests/failsafe.test.ts "an outage delays summaries, never clips them; a refusal clips".

5. The view: which lines a call sees

Read: Memory.fit, Memory.reach, Memory.merge, Memory.held, Memory.open, Memory.view, Memory.whole.

Two views

mem.view (turns) mem.seen (compactions)
high mark HIGH = 128,000 B SEEN = 32,000 B
after a batch at most 64,000 B at most 16,000 B
average size about 96 KB about 24 KB
reaches the last message (mem.count) the first unbuilt leaf of each side not held
saved in view.json parts view.json seen

Each view is a list of nodes that covers its messages with no gaps. A line that is not built yet is in the list but counts 0 bytes (Memory.size) and is left out of a request (Memory.view keeps only built lines).

Growth: append only

Memory.reach(view, end) appends one leaf (0, i) for each new message. Nothing else in the view changes. So between batches, the view of one call is a prefix of the view of the next call. This is what makes the cache work.

Shrink: one batch, from high to half

When a view passes its high mark, Memory.fit calls Memory.merge, which merges pairs until the size is at most half:

  • Which pair. A pair is two sibling lines (l, 2k) and (l, 2k+1), next to each other in the view, whose parent (l+1, k) is built. Its priority is d = (T + 1) / 2^l − i, with T the view's end. That is how long ago the pair ended, counted in its own line size. The largest d goes first; on a tie, the oldest. A heap over a linked list makes a batch of thousands of lines take milliseconds.
  • Why "ended" and not "started". optchat.md §3.2 shows that measuring from a pair's first message merges old pairs near ties, and rewrites old lines that should stay. Measured from the last message, the merges are exactly those of Taelin's rollback push, a binary counter. Each level then holds about as many lines as the next, so detail fades with age.
  • Only whole batches between messages. Memory.fit accepts a merged view only if it reached half (or, when parents are missing, at least dropped by high). If parents are missing, view.batch stays true, and the next message (Memory.push calls fit(mem, true)) merges what it can. Each change of the view makes every later call rewrite the view in the cache, so many small changes cost far more than one big one.
  • Each view merges on its own. The two views batch on their own high marks. A node that no view holds any more is dropped from memory (Memory.held), but never from disk.

Kept across restarts

Memory.save writes both views to view.json (written to .new, then renamed). Memory.load → Memory.open rebuilds each view by walking down from the roots and stopping at the nodes listed in the file. Without view.json, the fallback is "the highest nodes built". That view is valid, but it is a different view, so every cache entry dies once.

Where the view stops, and the new messages begin

The view does not reach the end of the chat in a turn. Memory.whole(mem, from) picks the first message from which the rest goes whole in the request: at most HIGH bytes and PICS = 20 images, and the last message always. The turn's view is Memory.view(mem, from), the lines before that point. For a normal message, from is the message itself. For a 300 KB paste, from falls inside the paste: its first pages are in the view as summaries (and must be built first), and only its tail goes whole.

6. The request, block by block

Read: Chat.call and Chat.share (src/server.ts), Tools.system, Tools.devices, Tools.at_work (src/tools.ts), Memory.view, Agent.loop, Anthropic.body, Anthropic.message, OpenAI.body.

A turn, step 1 (Anthropic)

Anthropic reads a request in this order: tools, then system, then messages. A cache entry is a prefix in that order.

Four marks, which is the most that Anthropic takes in one request (Memory.view puts one mark; Anthropic.body adds the system mark and the top-level one when the last block is marked). Adding a fifth makes the request fail.

Why each part is where it is:

  • Tools and system never change. There is no date, no device list, and no state in them. So mark 1 serves every turn of every chat on this model.
  • The view is in blocks of 4 lines (BLOCK), counted from the start of <chat>. The blocks stay aligned as the view grows: block k always holds lines 4k to 4k+3. So the blocks of the last turn come back byte for byte in the next turn, and only the new blocks are written.
  • The tail is not marked. Its 0-3 lines change on every turn. They are cheap to read again.
  • Per-turn state goes after the view. A device that joins or leaves changes only the end of the request, never the cached prefix (Tools.devices comment).

A turn, step k

Agent.loop keeps one array, items, for the whole call. Each step sends all of it:

  • Marks 1-3 stay put for the whole turn. Mark 4 (top-level) lands on the request's last block, so each step reads the step before from the cache and writes only the new tool round.
  • A message the user sends during the turn is not a new turn. Chat.take hands it to the running call (call.send), and Agent.loop adds it after the next tool results.
  • Thoughts are sent back within the turn (Anthropic needs its own thinking blocks with their signatures, items.push({ $: "Turn", out })), but they are never logged. So they die with the turn.

This is the "traditional" transcript: user, tool call, result, maybe a few more rounds, final text. It lives only in items, and only for one call.

The same turn on OpenAI

OpenAI.body puts a prompt_cache_breakpoint on each marked part and sends the system prompt as a developer message. The request's end is cached implicitly only if the last block is marked; if it is not marked (a compaction), prompt_cache_options: {mode: "explicit"} turns the implicit mark off. Reasoning keeps all turns (context: "all_turns"), so a message sent in the middle of a call does not drop it or miss the cache. TTL["openai-api"] is 30 minutes in our own model of the cache, against 5 for Anthropic.

7. The prefix state machine

This is the part that is easy to miss. The request is not one long transcript that grows forever. It has two shapes:

  • inside a turn, a normal transcript that grows at its end;
  • between turns, the transcript is thrown away, and its messages come back only as lines of the view.

What the cache does in each state

State Prefix sent Read from cache Written to cache
Step 1 of turn N tools, system, view(N), state, message tools + system (✱1); view blocks up to turn N−1's ✱2 new view blocks to ✱2; the rest to ✱3/✱4
Step k of turn N step k−1's request + one tool round all of step k−1's request (✱4 of step k−1) the new tool round
Turn N ends nothing nothing nothing; turn N's ✱3/✱4 entries are never read again and expire in 5 min
Compactions of turn N's messages system, seen view, task system (✱1, the compactor's own family); seen blocks up to an earlier ✱2 new seen blocks; the task is never cached
Step 1 of turn N+1 tools, system, view(N+1), state, message tools + system; view(N) blocks up to its ✱2 turn N's messages, now as leaf lines, and the rest
After a batch as above tools + system only the whole view, once

A worked example

Turn N starts at message 100, and the view ends at line 99:

step 1:  … | 96+1|… 97+1|… 98+1|… 99+1|… | Turn: the user's new message: fix the build
step 2:  … same … | assistant: tool_use shell {"cmd":"bun test"} | user: tool_result "3 fail …"
step 3:  … same … | assistant: tool_use edit {…} | user: tool_result "ok"
step 4:  … same … | assistant: "Fixed: the import path in x.ts was wrong."

As it ran, Chat.on logged:

100 user: fix the build
101 tool: shell {"cmd":"bun test"}
102 echo: 3 fail … (12 KB)
103 tool: edit {…}
104 echo: ok
105 ever: Fixed: the import path in x.ts was wrong.

In the background: 100, 101, 103, 104, and 105 are short, so their leaves are free and word for word. 102 is long, so the compactor writes its leaf. Pairs are merged as they complete: 100+2 from 100 and 101, 102+2 from 102 and 103, then 100+4, and so on.

Turn N+1 starts at message 106. Memory.settle waited for 102's leaf. Its request:

… | 96+1|… 97+1|… 98+1|… 99+1|… 100+1|user: fix the build 101+1|tool: shell {"cmd":"bun test"}
  102+1|echo: bun test: 3 failures in x.test.ts, all "cannot find module ./y" …
  103+1|tool: edit {…} 104+1|echo: ok 105+1|ever: Fixed: the import path … | Turn: … <msg 106>

The transcript of turn N is gone: no tool_use, no tool_result, no thoughts. What is left is six lines of the view. Those lines are a few hundred bytes, against the 12 KB result. That is the fold. Later, a batch replaces 100+1 … 103+1 with 100+4, and later still with 96+8.

Important

The view's lines were appended: lines 0-99 are byte for byte the same as in turn N. That is why turn N+1 reads them from the cache. If anything changed a line before 100 (a batch, a rebuilt view, a different system prompt), the read would stop at that line, and everything after it would be written again at 1.25× the price.

The other calls

  • A subagent (Tools.ask, src/tools.ts) has its own system prompt (SUB), the view as it was when the subagent was spawned, the devices, and its own log (Memory.agent_show, marked). Its steps go to docs/agent/<Name>.jsonl, not to the chat. Only its report comes back, as one work message.
  • A goal check (Chat.check) has its own system prompt (GOAL) and no tools. It sends the view up to Memory.whole(mem, 0) and the messages after that, word for word.

8. Single flight: one writer per prefix

Read: AskAI.keys, AskAI.wait, AskAI.lead, Agent.request, Agent.stream (begun). Test: tests/failsafe.test.ts "a request leads single flight only as it is sent"; tests/cache.test.ts.

The problem: up to 64 compactions start at once, often on the same view prefix. If they all go out together, each one pays to write the same cache entry (1.25×), because none of them can read an entry that is not written yet.

The fix keeps a local model of the vendor's cache (CACHE in src/askai.ts):

  1. AskAI.keys(ask) hashes the request's head (vendor, model, effort, speed, system, web search on or off), then each block in a chain, up to the last mark before the end. Key k is the prefix up to block k.
  2. AskAI.wait finds the longest key that is live. If a leader is still writing it, the request waits until the leader's response begins (message_start on Anthropic). Only then can the vendor serve the entry.
  3. If the whole prefix is cached, the request goes at once. Otherwise it becomes the leader of its last key.
  4. A request becomes a leader only once it is really being sent: after its payer let it through, and not while it yields to a busy model. If it waited on credit while holding the lead, it would block every other call on that prefix.

9. Where optchat.md and the code differ

optchat.md is the design note. The code came later, and it is what runs.

Topic optchat.md says The code does Where
Compaction cache "the same system prompt and tools … so it reads them from the turns' cache entry" Same system text, but no tools and a different model (COMPACTOR, haiku, versus the chat's pick, sonnet by default). Anthropic caches by model, and tools come first in the prefix. So compactions never read the turns' entries. They share only with each other. Chat.share, Memory.ask, config.ts
Why no tools (not said) A compaction that called a tool would send its whole input again. Chat.share comment
Jobs at once 8 JOBS = 64 per side (chat, import) memory.ts
Retry of a long line "send this in the same conversation" A fresh request: the same blocks plus a note with the size and the cut. Never the earlier answer or thoughts. Memory.build, Memory.over
Failed call "tried again at the next message" Patient: asked again every 60 s until answered. A refusal clips the source to 512 B. A payer's refusal holds the side. AskAI.ask, Memory.build
Compactions' view merged again "when the chat's view merges" Merges only on its own high mark (32 KB). Memory.fit
Cache marks one on the last whole block, one on the request's end Four: system, last whole view block, the message's end, top-level. Anthropic.body, Memory.view
Whole messages "the view holds only summaries … The message goes whole after it" Memory.whole decides how much goes whole: up to 128 KB and 20 images. A huge paste is partly summarized. Memory.whole, Chat.call
Compactor effort Haiku at xhigh haiku-5.5:high:slow config.ts
Kinds unii, … ever (4 bytes), plus ai for an imported AI and mind (never logged) askai.ts Kind, Memory.show
Per-turn state "after the view" After the view: the devices and agents at work, then Turn: the user's new message: Chat.call
Compaction prompt (verbatim in §5) The same, plus a last paragraph: "This is a small, mechanical job … Be fast and spend few tokens". src/prompt.txt
Tip

The first row matters for upstream PR #37 (a separate compaction prompt). optchat.md's main reason to share one prompt was to share the cache. The code already does not share it, because the model differs. So a separate prompt costs nothing in cache terms. See upstream-issues-and-prs.md.

10. Mistakes to avoid

Each entry says what goes wrong, how the code avoids it, and where to look. Entries 1-13 are optchat.md's list, made concrete. The rest come from the code.

The tree and the view

1

Measuring a pair's age from its first message.

Old lines churn, and the view rewrites lines that should stay.

Fix Memory.merge uses (T + 1) / 2^l − i, which is the age from the pair's last message. If you change the formula, check it against Taelin's push (optchat.md §3.1) for t = 0 to 20,000.

2

Merging at every message.

Each merge changes the view from the merged line on, so every call after it writes the view again. Small merges at every message rewrite about 53 of 192 lines per message; one batch rewrites about 2 per message on average (optchat.md's simulation).

Fix Memory.fit merges only when a view passes high, and only to half.

3

Rebuilding the view, at each turn or at a restart.

A rebuilt view differs from the live one, and every cache entry dies.

Fix Memory.save after each change; Memory.load → Memory.open from view.json. Never delete view.json to "fix" something.

4

Keeping K lines per level.

The view then grows forever with the log's depth.

Fix A byte budget (HIGH), not a line count.

5

Whole messages in the view, or half a message.

One 30 KB result in the view forces dozens of merges that never split back. Half a message makes the model act on half a message.

Fix The view holds only built nodes (Memory.view filters on Memory.built). A turn waits for Memory.settle. A compaction's view stops at the first unbuilt leaf. Pages wait for their last page (more).

6

A compaction without context.

"Do it" and "that file" cannot be resolved, so the line is vague forever.

Fix mem.seen, 16-32 KB of the chat up to the node's ctx.

7

Trusting the model to count bytes.

→ The 512-dash ruler (SCALE), the cut note (Memory.over), at most 5 tries, and the shortest line kept. Note: a ruler made of a sample line got its content copied into the summaries, so the ruler is dashes.

8

Lines under 512 bytes.

At 128 bytes the model could not write useful lines.

Fix NODE = 512. If you lower it, every level loses detail.

9

Logging thoughts.

They add little, they cost bytes, and summarizing them drew safeguard refusals.

Fix Chat.on shows mind and never pushes it.

10

Dates or state in the system prompt or the tools.

Every turn would miss the cache from byte 0.

Fix The date is a tool (date(id)). Devices and agents at work go after the view. See also mistake 16.

11

Carrying a conversation across turns.

The context grows without bound and rots, and the transcript's prefix changes as soon as the view does.

Fix items lives in Agent.loop only. Each turn is a fresh call. The view is the only continuity.

12

Two writers on one log, or a write without a flush.

→ One process owns a chat. The logs are append only, and Disk flushes in groups. An act is answered only after its flush.

13

Scanning the tree for work.

Over a long chat that is O(N²).

Fix mem.ready: sorted queues by side and level, kept up to date by Memory.ready and Memory.store. Memory.todo walks the tree only once, at load, and visits only unbuilt nodes.

The cache

14

Moving a block boundary.

If blocks were cut by bytes, or counted from the end, appending one line would shift every boundary, and no block hash would match the last turn's.

Fix Memory.view cuts blocks of BLOCK = 4 lines from the start of <chat>.

15

A fifth cache mark.

Anthropic takes four per request. A fifth fails the request.

Fix Memory.view puts exactly one mark. Before you mark the devices block or a subagent's part, count the marks.

16

Changing the system prompt while the server runs.

Tools.system appends the user's rules file, and Tools.rules reads that file on every call. Editing the file changes the system prompt at once, and every chat's cache misses from byte 0, for turns and compactions alike.

Fix Edit rules rarely, and expect one expensive call per chat after each edit.

17

Something in the prefix that the cache key does not include.

AskAI.keys hashes the vendor, model, effort, speed, system prompt, whether web search is on, and the blocks, but not the tool list. That is safe today, because the tool list is the same for every call of a kind. If tools ever vary per chat (MCP servers, upstream PR #39), two calls with different tools would look like one prefix, and single flight would make one wait on the other for nothing.

Fix Add the tool definitions to the key's head when tools become dynamic.

18

Treating the compactor's cache as the turns' cache.

See §9, first row. Cost estimates that assume compactions read the turns' system prompt from the cache are wrong.

19

Too many new lines between two turns (to check).

Anthropic looks back at most about 20 blocks from a mark for an earlier entry (optchat.md §3.3; LOOK = 20 in tests/cache.test.ts). With 4 lines a block, that is 80 lines. A turn that logs more than about 80 messages (40 tool calls and their results) moves the next turn's view mark more than 20 blocks past the last one. The view would then likely be written again. This is not measured yet. To check: log use.write and use.read on the first step of the turn after a long turn.

Turns and compactions

20

Starting a turn before its view is built.

→ Chat.call loops on Memory.settle until from stops moving (a message that arrives meanwhile can move it). If the side is held (no credit), the turn is told why at once instead of waiting forever (tests/failsafe.test.ts "a turn waiting on summaries held for credit is told so at once").

21

Clipping a node because the vendor was down.

A clipped node is lost detail, forever.

Fix Patient calls: an outage only delays. Only a refusal (the model answered and failed) clips.

22

Many compactions that lag their context.

With JOBS = 64, a leaf can start while up to 63 leaves before it are unbuilt, and its view stops at the first unbuilt one. So in a burst (an import, a fast tool loop with long results), a leaf can be written without the messages just before it. Usually the gap is small, because short messages are built at once with no call.

Fix If summaries in bursts lose context, lower JOBS. That trades speed for context.

23

Sending a retry as a conversation.

The model's long answer and its thoughts would go into the prefix, and the retry would pay for them.

Fix Memory.build sends the same blocks plus one note.

24

A tool call logged apart from its result.

They could land in different subtrees and be summarized apart.

Fix Chat.on holds the call in at.calls until its result comes, then logs both. A call stopped before its result is logged alone at the end (Chat.unanswered).

11. A reading order

  1. references/optchat.md, §1-§4. The intent.
  2. src/memory.ts, top to bottom. It is long, but it is in order: log, tree, compactions, view, zoom. Keep §3-§5 of this document open.
  3. src/askai.ts: keys, wait, lead. The cache model.
  4. src/agent.ts: loop, step, send. The transcript inside a turn.
  5. src/anthropic.ts: body, message. Where the marks become cache_control.
  6. src/server.ts: Chat.take, Chat.call, Chat.on, Chat.share. Where a turn is put together.
  7. tests/cache.test.ts: a fake Anthropic cache with the same rules, replaying a chat. It checks that turns and compactions read at least 95% from the cache. Change the marks or the view, then run it (just test tests/cache.test.ts).
